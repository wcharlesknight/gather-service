# Multi-City Expansion Plan

## Overview
The Gather Service is designed to start in Seattle and expand to multiple cities. This document outlines the technical approach for scaling to multiple cities.

## Current State (Phase 1)
- **Single City**: Seattle, WA
- **Single Topic**: `weekly-gather`
- **Single Schedule**: Monday 9:00 AM PST
- **Search Term**: bars
- **Limit**: 50 results

## Technical Considerations

### Timezone Management
- Store cron expressions in local time per city
- Convert to UTC for scheduling
- Display times to users in their local timezone
- Use `ZoneId` for each city

**Example**:
```java
ZoneId seattleZone = ZoneId.of("America/Los_Angeles");
ZoneId newYorkZone = ZoneId.of("America/New_York");

// 9 AM Monday Seattle = 12 PM Monday New York
```

### Avoiding Repeats ✅ (Already Implemented)
**Strategy**: Don't select a spot that was chosen in the last 12 weeks

**Current Implementation**:
```java
private YelpBusiness selectRandomGatheringSpot(
    List<YelpBusiness> businesses,
    String cityId
) {
    if (cityId != null) {
        // Get recent Yelp IDs from Firestore (last 12 weeks)
        List<String> recentYelpIds = gatheringSpotRepository
            .findRecentYelpIds(cityId, avoidRepeatWeeks);

        // Filter out recent selections
        List<YelpBusiness> available = businesses.stream()
            .filter(b -> !recentYelpIds.contains(b.getId()))
            .collect(Collectors.toList());

        if (!available.isEmpty()) {
            businesses = available;
            logger.info("Filtered to {} available spots", businesses.size());
        } else {
            logger.warn("All spots recently used, using full list");
        }
    }

    // Random selection from available spots
    return businesses.get(random.nextInt(businesses.size()));
}
```

**Firestore Query**:
```java
public List<String> findRecentYelpIds(String cityId, int weeksBack) {
    long cutoffTime = System.currentTimeMillis() -
        (weeksBack * 7 * 24 * 60 * 60 * 1000L);

    return firestore.collection("gatheringSpots")
        .whereEqualTo("cityId", cityId)
        .whereGreaterThan("selectedAt", cutoffTime)
        .get()
        .stream()
        .map(doc -> doc.getString("yelpBusinessId"))
        .collect(Collectors.toList());
}
```

### Performance & Scaling

**Current Load** (Single City):
- 1 Yelp API call per week
- N push notifications (where N = number of subscribers)
- Minimal database queries

**Projected Load** (10 Cities):
- 10 Yelp API calls per week
- Still well within Yelp free tier (5000/day)
- ~100 Firestore reads per week (checking recent spots)
- ~10 Firestore writes per week (saving selections)
- Firebase FCM has no practical limit

**Scaling Bottlenecks**:
- Yelp API rate limits (5000/day = plenty of room)
- Firebase FCM (unlimited notifications on free tier)
- Firestore (free tier: 50k reads, 20k writes per day)
- Firestore storage (1 GB free, ~5,200 records = <1 MB)
- Server resources (minimal - Spring Boot app is lightweight)

**Cost Analysis**:
- Current usage: $0/month (well within free tiers)
- 10 cities: $0/month (still within free tiers)
- 50 cities: $0/month (Firestore reads: ~2,600/month, writes: ~260/month)
- 100 cities: ~$5/month (may exceed Firestore free tier slightly)

**Recommendation**: Current architecture scales easily to 50+ cities on free tier
